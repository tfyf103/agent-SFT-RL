# 架构与研究边界

## 1. 产品切片

当前实现是客户提交工单、员工处理工单的**可执行研究环境**。它具备两种身份、
统一工具契约和状态验证，不是完整的生产客服网站，也没有接入原 Django/Vue
项目源码。原聊天平台可以将模型调用层替换为 ChatPolicy 并接入同一工具网关，
但本仓库不能声称那项系统迁移已经发生。

首版只研究信息补全与执行恢复，避免把交易、授信审批等真实写操作纳入演示。
金额阈值、规则版本、客户和员工身份全部由合成数据生成器定义。

## 2. 一次任务如何走完

用户请求 → 带身份的 BankEnv → Agent 生成 JSON action → 服务端检查工具参数与权限
→ 查询模拟知识/工单或提交状态变更 → 工具观测加入下一轮上下文 → 最终状态验证。

- 身份由 task 的 principal_id 建立，LLM 无权通过 arguments 改身份。
- 客户只能访问自己的工单；员工只能访问分配给自己的工单。
- search_policy 返回角色适用的合成规程、版本、材料要求和阈值。
- get_case 读取有权限的当前业务事实。
- collect_materials 是明确标记的合作型用户模拟器，不是真实客户对话模型。
- submit_case / resolve_case 进行确定性前置检查和幂等写入。
- get_status 确认真实持久状态；finish 只是模型对结果的声明。

不能把“后端拦下越权”当成“模型已经学会权限控制”。本系统隔离控制与决策策略，
所有对照共享完全相同的权限检查和写入规则。

## 3. 四类故障的差异

| 故障 | 真实状态 | 可见反馈 | 合理恢复 |
|---|---|---|---|
| read_timeout | 未读取 | READ_TIMEOUT | 重试读取 |
| write_timeout | 未提交 | WRITE_TIMEOUT（结果未知） | 查询状态后使用原请求ID重试 |
| lost_ack | 已提交 | 同样的 WRITE_TIMEOUT | 查询状态，避免把结果未知当作失败 |
| policy_change | 新版本已生效 | STALE_POLICY | 重新检索、重新计算动作参数 |

模型不知道 task.faults，也看不到 expected status。两种写入故障故意返回相同文本，
要求决策依赖后续查询。幂等键来自服务端 request_id，并对重复写入保持相同结果。

## 4. 成功条件

已授权任务：最终状态正确、恰好一次有效写入、已收到成功回执或状态查询证据、finish 声明与实际状态一致。
不要求完全照抄参考控制器的工具顺序；例如收到明确成功回执后结束也可能正确。
未授权任务：实际访问被拒绝，没有写入，并正确转人工说明 access_denied。

正常授权任务成功率与未授权请求正确处置率分别统计。超时、截断、解析失败
保留在分母。合法任务的转人工算误拒，不会借拒绝刷成功率。

search_policy/get_case 等前置检查属于这一模拟流程的固定规则，
其通过不能推导模型在真实银行中具备泛化的合规能力。

## 5. 四个不同的证据层

1. 脚本控制实验：验证环境规则和恢复机制；没有训练模型。
2. CPU 小策略实验：可观测特征上的有限动作策略，真实SFT及组相对策略梯度；
   参数绑定仍由程序完成，不证明自然语言理解或LLM工具调用能力。
3. 135M 语言模型 CPU smoke：若云端作业完成，仅证明训练、mask和保存路径可用；
   短运行不证明银行业务指标改善。
4. 大模型 SFT/GRPO 与官方 tau 外测：必须有真实运行日志与独立任务结果才能报告。
   提供脚本不等于完成复现。

## 6. 数据划分能力与限制

生成器先固定 train/valid/test/stress，再产生独立实体和表述；stress 用训练中
未共同出现的故障组合。规程文本在推理时可查，检查的是条件执行能力。
各集合仍共享两个基本业务流程和语言模板风格，因此只能称“合成环境留出”，
不能写“未见真实业务场景泛化”。官方 tau-Knowledge 全部留作独立外部评测。
