## 第二轮：15分钟跑客户案例

在仓库根目录：
```bash
python -m pip install -e ".[dev,toy]"
python -m scripts.demo --role customer --mode recovery
python -m scripts.demo --role customer --mode open_loop
```

逐条说出：它读取了什么证据、为什么需要补材料、提交是否真正写入、WRITE_TIMEOUT
是不是等价于“没成功”、为什么下一步查状态、为什么重试必须复用同一request_id。
然后运行员工案例：
```bash
python -m scripts.demo --role employee --mode recovery
```
对比客户只能提交、员工按当前规程选择 resolved/escalated。解释权限不是prompt决定的。

关键追问：为什么直接重试可能有问题？
答：网络超时可能发生在提交前，也可能发生在提交后回执丢失。应用端无法仅根据
超时文本判断，需查状态与幂等键协作。当前模拟器故意让两种情况返回相同错误码。

## 第四轮：20分钟理解SFT

SFT训练样本是一条 messages 轨迹。上下文包括system、用户和工具返回；
损失只作用于助手需要生成的动作文本。工具返回作为条件，但不让策略“学习生成”
环境的观测内容。labels=-100 跳过非助手位置，与attention mask是两个不同概念。

先理解：
L_SFT = -平均 log p(助手token | 当时的完整上下文)。

为什么要保留错误恢复轨迹？
如果只展示理想成功路径，模型没有学习“工具失败后怎么继续”的监督。
使用相同训练样本/更新预算比较正常数据和恢复数据，才能较好区分数据结构与规模收益。

为什么chat template会出错？
模板会插入角色与结束标记；直接拼接字符串或重复分词容易错位。
本实现检查模板前缀，不能可靠构造mask时直接报错，不静默把用户内容算入损失。

训练loss下降能证明任务成功率提高吗？
不能。可能只学会格式或记住模板。必须用独立任务重新rollout并检查终态。

## 第五轮：20分钟理解多轮RL

单个prompt/task采样G条轨迹，每条最终得到一个奖励r。
组相对优势 A_i=(r_i-mean(r))/(std(r)+epsilon)。
终局奖励回传到该轨迹助手动作的token上，环境观测不参与策略损失。

本仓库两种不同算法：
- CPU小策略：group-relative REINFORCE，有限动作分布；如果没有PPO clip就不能叫完整GRPO。
- 语言模型参考训练：保存采样时token与old logprobs，使用clipped ratio更新并约束reference KL。
  这是易审查的单设备实现；高吞吐另走Slime，不声称有分布式性能优化成果。

为什么旧策略和参考策略不同？
旧策略是产生当前rollout数据的策略，用于importance ratio；reference是冻结的锚，
用于限制更新偏离。每轮采样可更新old，reference不跟着每次优化一起更新。

一组全失败怎么办？
优势全0，没有任务学习信号。应记录零方差组比例，改善基础SFT或任务课程。
调高奖励数字不会凭空产生正确行为。

为什么不能奖励“调用了多少次工具”？
容易鼓励无效查询。奖励以正确终态为主，效率作为独立指标或小权重消融项。
拒绝合法请求不算成功；未授权请求正确处置单独统计。

多轮context中的工具token为什么还占显存？
不计算其loss不代表不参与前向；后续动作仍要以其为条件。长轨迹增加KV缓存、
激活和重复上下文计算，不能用“mask掉了”解释显存没有开销。

## 第六轮：10分钟讲实验与边界

能说清五件事：数据划分、基线、改动、证据、限制。
- 基线是不是同一个模型/提示/环境/用户模拟器/预算？
- 在测试集上调过哪些参数？正确做法是train/valid选择，test一次最终评测。
- 为什么脚本控制100%不等于大模型100%？它直接编码了这个有限环境的规则。
- 为什么很多失败仍然writes=0？后端阻止错误写入，模型本身仍可能反复错误尝试。
- RL没有提升时怎么讲？当前恢复SFT与恢复SFT+RL的greedy成功率都是100%，
  因而没有额外成功率收益；结合训练日志检查零优势组，不把负结果换成公开论文中的正结果。
- 55.89% ± 5.63是什么意思？三种子Test授权成功率的均值和种子间样本标准差，
  每种子分母为164个授权任务；不是置信区间，也不是全部客户成功率。

## 常见追问与回答要点

**这是RAG还是Agent？** 检索只是工具之一；策略根据观测决定后续动作并改变环境状态。
当前search_policy是确定性模拟知识工具，不能声称做了真实向量检索召回优化。

**为什么需要用户模拟器？** 多轮任务会要求补充材料或确认；这里先用确定性合作型模拟器，
便于重现故障。官方tau外测另用固定用户模型，结果不混报。

**为什么没有直接照搬tau任务训练？** 银行上游任务划分接口存在版本细节，
当前方案将其留作外部测试，避免训练见过同一道测试任务。

**SFT与RL分别解决什么？** SFT用示范教会基本格式和执行方式；RL根据实际执行结果调整策略。
两者能否提升必须由同条件对照验证。

**越权率为0说明模型安全吗？** 不说明。实际写入被网关保护与模型尝试越权是两件事。
还要看越权尝试、合法误拒及工具参数的正确性。

**为什么不直接做更多多Agent？** 当前问题是可定位的执行恢复，一个决策策略已足以研究。
增加角色协作需要额外证明收益，双用户角色并不等于两个LLM Agent。

**pass@4与pass^4有什么区别？** 前者至少一次成功，后者四次都成功。逐任务重复统计，
不能直接把总体成功率四次方。确定性脚本重复四次不是可靠性采样实验。

**能否对外说服务了北京银行？** 当前不能。没有生产部署/真实用户记录，
只能说面向银行场景的研究原型，制度和账户为模拟。
